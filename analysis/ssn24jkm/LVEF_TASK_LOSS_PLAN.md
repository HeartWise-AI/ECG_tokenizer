# LVEF Task-Aware Loss Implementation Plan

## 1. Current LVEF Data Format

### Dataset Columns
The training parquet (`combined_train_qa_m5000k_h5000k_weighted.parquet`, 7.27M rows) and test parquet (`combined_test_qa_m25k_h25k.parquet`, 49,776 rows) both contain:
- `prompt_category`: string column; value `"lvef"` identifies LVEF samples (197,422 train / 2,656 test)
- `deepecho_Visually_Estimated_EF`: float column with ground truth LVEF (range 10-75, mean ~51.4, std ~12.3)
- `prompt`: one of 5 question templates (e.g., "What is the patient's left ventricular ejection fraction?")
- `generated_answer`: always follows the format `"The left ventricular ejection fraction is XX% (category)"`

### Answer Format (Deterministic)
Generated by `ecg_answer_generator.py:generate_lvef_answer()` at line 2207:
```
"The left ventricular ejection fraction is {lvef_rounded}% ({category})"
```
Where `lvef_rounded = round(float(deepecho_Visually_Estimated_EF))` and category is one of:
- `normal` (>= 55)
- `mildly reduced` (45-54)
- `moderately reduced` (30-44)
- `severely reduced` (< 30)

### MedGemma Tokenization of LVEF Answers

All LVEF values (10-75) are 2-digit numbers. MedGemma tokenizes each digit as a separate token:

| Token Position | Token ID | Content |
|---|---|---|
| 0 | 818 | "The" |
| 1 | 2378 | " left" |
| 2 | 61524 | " ventricular" |
| 3 | 132777 | " ejection" |
| 4 | 10742 | " fraction" |
| 5 | 563 | " is" |
| 6 | 236743 | " " (space) |
| **7** | **varies** | **tens digit** |
| **8** | **varies** | **units digit** |
| 9 | 236908 | "%" |
| 10+ | ... | " (category...)" |

**Digit token IDs** (MedGemma vocab, IDs ~236770-236832):
```
digit 0 -> 236771    digit 5 -> 236810
digit 1 -> 236770    digit 6 -> 236825
digit 2 -> 236778    digit 7 -> 236832
digit 3 -> 236800    digit 8 -> 236828
digit 4 -> 236812    digit 9 -> 236819
```

**Critical property**: The LVEF number is always exactly 2 tokens (tens digit + units digit), immediately preceded by a space token (236743) and followed by `%` (236908). This is invariant across all LVEF values 10-75.

```python
def _ensure_digit_token_ids(self):
    """Build digit-to-token-id mapping from the tokenizer. Called once lazily."""
    if self._digit_token_ids is not None:
        return
    # Encode each digit 0-9 as a standalone token
    self._digit_token_ids = []
    for d in range(10):
        ids = self.tokenizer.encode(str(d), add_special_tokens=False)
        assert len(ids) == 1, f"Digit {d} encodes to multiple tokens: {ids}"
        self._digit_token_ids.append(ids[0])
    # '%' and space tokens for anchor detection
    pct_ids = self.tokenizer.encode('%', add_special_tokens=False)
    self._pct_token_id = pct_ids[0] if pct_ids else None
    # The standalone space that appears before the number
    space_ids = self.tokenizer.encode(' ', add_special_tokens=False)
    self._space_token_id = space_ids[0] if space_ids else None
```

### Step 4: Implement soft-decoded LVEF extraction (the core algorithm)

Add this method to `MedGemmaDecoder`:

```python
def _compute_lvef_soft_loss(
    self,
    logits: torch.Tensor,       # [B, seq_len, vocab_size]
    labels: torch.Tensor,       # [B, seq_len] with -100 for ignored positions
    lvef_gt: torch.Tensor,      # [B] ground truth LVEF values (NaN for non-LVEF)
) -> Optional[torch.Tensor]:
    """
    Compute differentiable Huber loss between soft-decoded LVEF and ground truth.

    For each LVEF sample in the batch:
    1. Find the position of the '%' token in the labels
    2. The two positions before '%' are the units and tens digits
    3. Compute softmax over digit token IDs at those positions
    4. Expected value = sum(prob_i * i) for each digit position
    5. Predicted LVEF = tens_digit * 10 + units_digit
    6. Huber loss against ground truth

    This is fully differentiable through the logits via softmax.
    """
    self._ensure_digit_token_ids()

    device = logits.device
    batch_size = logits.size(0)
    digit_ids = torch.tensor(self._digit_token_ids, device=device)  # [10]
    digit_values = torch.arange(10, dtype=torch.float32, device=device)  # [0..9]

    losses = []

    for b in range(batch_size):
        gt = lvef_gt[b].item()
        if gt != gt:  # NaN check (faster than torch.isnan for scalar)
            continue

        # Find '%' token position in labels (not -100)
        sample_labels = labels[b]  # [seq_len]
        pct_positions = (sample_labels == self._pct_token_id).nonzero(as_tuple=True)[0]

        if len(pct_positions) == 0:
            continue

        # Take the first '%' occurrence
        pct_pos = pct_positions[0].item()

        # The two positions before '%' are units_digit (pct_pos-1) and tens_digit (pct_pos-2)
        if pct_pos < 2:
            continue

        units_pos = pct_pos - 1  # position in labels where units digit token sits
        tens_pos = pct_pos - 2   # position in labels where tens digit token sits

        # Verify these are actual digit tokens in labels (sanity check)
        tens_label = sample_labels[tens_pos].item()
        units_label = sample_labels[units_pos].item()
        if tens_label not in self._digit_token_ids or units_label not in self._digit_token_ids:
            continue

        # In causal LM, logits[t] predicts token at position t+1.
        # BUT: HuggingFace internally shifts labels by 1 when computing CE loss.
        # The labels tensor we receive is ALREADY aligned: labels[t] is the target for logits[t].
        # Actually, HF does: loss = CE(logits[:-1], labels[1:])
        # So logits[t] predicts labels[t+1].
        # To predict the token at labels[tens_pos], we need logits[tens_pos - 1].

        # HOWEVER: the labels tensor has been shifted by the ECG prefix injection.
        # We need to be careful about alignment. Let's use the simpler approach:
        # Find positions where labels match the digit tokens, then use logits at pos-1.

        # For Gemma/GPT-style models: logits[i] predicts the next token (position i+1)
        # So logits at position (tens_pos - 1) predicts the token at tens_pos
        tens_logit_pos = tens_pos - 1
        units_logit_pos = units_pos - 1

        if tens_logit_pos < 0 or units_logit_pos >= logits.size(1):
            continue

        # Extract logits at digit positions, indexed only over digit vocabulary
        tens_logits = logits[b, tens_logit_pos, digit_ids]   # [10]
        units_logits = logits[b, units_logit_pos, digit_ids]  # [10]

        # Softmax to get probabilities (differentiable)
        tens_probs = torch.softmax(tens_logits.float(), dim=0)   # [10]
        units_probs = torch.softmax(units_logits.float(), dim=0)  # [10]

        # Expected value: E[digit] = sum(prob_i * i)
        predicted_tens = (tens_probs * digit_values).sum()    # scalar
        predicted_units = (units_probs * digit_values).sum()  # scalar

        # Predicted LVEF = tens * 10 + units
        predicted_lvef = predicted_tens * 10.0 + predicted_units  # scalar, differentiable

        # Ground truth
        gt_tensor = torch.tensor(gt, dtype=torch.float32, device=device)

        # Huber loss (smooth L1) - less sensitive to outliers than MSE
        loss = torch.nn.functional.huber_loss(
            predicted_lvef, gt_tensor, reduction='none', delta=5.0
        )
        losses.append(loss)

    if not losses:
        return None

    return torch.stack(losses).mean()
```

## 4. Tokenizer Mapping Details

### Digit Token ID Table (MedGemma `google/medgemma-4b-it`, vocab size 262,145)

```python
DIGIT_TOKEN_IDS = {
    0: 236771,
    1: 236770,
    2: 236778,
    3: 236800,
    4: 236812,
    5: 236810,
    6: 236825,
    7: 236832,
    8: 236828,
    9: 236819,
}
```

These are verified to be single-token encodings (each digit maps to exactly 1 token). The IDs are in the 236K range, which is part of Gemma's byte-level fallback vocabulary.

### Anchor Token for Position Finding

The `%` token (ID 236908) is the definitive anchor. In every LVEF answer, the pattern is:
```
... " " [tens_digit] [units_digit] "%" ...
     ^        ^            ^         ^
  236743   varies       varies    236908
```

**Position finding algorithm**: Scan `labels` for token 236908 (`%`). The two preceding non-ignored positions contain the digit tokens. This is robust because:
1. `%` appears exactly once in LVEF answers
2. It always immediately follows the 2 digit tokens
3. No other answer format in the dataset uses `%` after digits

### Label Alignment

HuggingFace causal LM loss uses: `loss = CE(logits[:, :-1, :], labels[:, 1:])`. This means:
- `logits[b, t, :]` predicts the token at `labels[b, t+1]`
- To predict the tens digit at `labels[b, tens_pos]`, use `logits[b, tens_pos - 1, :]`

The labels tensor in this codebase has prompt positions set to -100 (ignored for CE), but the answer tokens retain their actual token IDs. ECG prefix tokens are also -100. So finding `%` in labels reliably locates the LVEF answer portion.

## 5. Loss Weight Recommendations

### Recommended Starting Configuration

```yaml
lvef_loss_weight: 0.1
```

### Rationale

- **CE loss magnitude**: Typically 1.5-3.0 for this model during training
- **LVEF Huber loss magnitude**: With `delta=5.0`, for errors of ~10 EF points (common early in training), Huber loss is ~7.5. For errors of ~20 points: ~17.5.
- **At weight 0.1**: LVEF loss contribution is ~0.75-1.75, which is 25-60% of CE loss. Significant but not dominant.
- **Gradient flow**: The soft-decoding creates gradients that specifically push digit logits toward the correct value, complementing the argmax-based CE loss which treats all wrong digits equally.

### Scaling Considerations

| Weight | Behavior | Risk |
|--------|----------|------|
| 0.01 | Minimal impact, safe starting point | May be too weak |
| 0.05 | Mild nudge toward correct LVEF | Conservative |
| **0.1** | **Balanced: meaningful LVEF signal without disrupting CE** | **Recommended start** |
| 0.3 | Strong LVEF emphasis | May hurt other tasks |
| 1.0 | LVEF-dominant | Will degrade non-LVEF tasks |

### Huber Delta Parameter

`delta=5.0` means:
- Errors < 5 EF points: quadratic loss (MSE-like), strong gradient for fine-grained correction
- Errors > 5 EF points: linear loss, avoids gradient explosion from large errors early in training

Alternative: `delta=10.0` for a wider quadratic region if predictions are consistently off by >5.

### Batch Composition

LVEF samples are ~2.7% of the training data (197K / 7.27M). In a batch of 8, on average 0.22 samples are LVEF. The loss will be sparse -- many batches will have zero LVEF loss. This is acceptable because:
1. The CE loss still trains LVEF token prediction in those batches
2. When LVEF samples appear, the soft loss provides a strong corrective signal
3. Over many steps, the gradient statistics accumulate properly

**Optional enhancement**: If the sparse signal is insufficient, consider increasing LVEF sample weight in `dataset_weights` or using weighted sampling to ensure ~1 LVEF sample per batch.

## 6. Risk Assessment and Testing Plan

### Risks

| Risk | Severity | Mitigation |
|------|----------|------------|
| **Label alignment off-by-one**: Logit position vs. label position mismatch | HIGH | Unit test: encode a known LVEF answer, verify predicted digit matches label |
| **ECG prefix shifts positions**: Injected ECG embeddings shift all positions | HIGH | The `labels` tensor already accounts for prefix (prompt positions are -100). `%` position in labels is stable. |
| **NaN propagation**: If `lvef_gt` NaN leaks into loss | MEDIUM | Explicit NaN filtering before loss computation; skip entire batch contribution if no valid LVEF samples |
| **Gradient explosion**: Large LVEF errors early in training | LOW | Huber loss with delta=5.0 caps gradients; weight 0.1 limits magnitude |
| **Collate failure**: `float('nan')` in dict may fail collation | LOW | PyTorch `default_collate` handles float tensors with NaN; verified |
| **Multi-GPU sync**: LVEF loss present on some GPUs but not others | MEDIUM | Return loss=0 (not None) when no LVEF samples, so DDP allreduce doesn't hang |
| **`%` token appears in non-LVEF answers**: False positive anchor detection | LOW | Only compute when `lvef_gt` is non-NaN, which only happens for `prompt_category='lvef'` |

### Critical Implementation Detail: DDP Safety

When some GPUs in a DDP group have LVEF samples and others don't, the loss tensor must still participate in the backward pass for gradient synchronization. The implementation must return a zero-gradient tensor rather than `None`:

```python
# In _compute_lvef_soft_loss, if no valid LVEF samples:
if not losses:
    # Return a zero tensor that still has grad_fn for DDP compatibility
    return torch.tensor(0.0, device=logits.device, requires_grad=True) * logits.sum() * 0
```

Actually, the simpler approach (returning `None` and not adding to the loss) is safe because the base CE loss always participates in backward. The LVEF loss is additive -- its absence doesn't break DDP.

1. Large sample size (197K train)
2. Highly structured answer format (invariant template)
3. Clinical importance (EF is a key cardiac metric)
4. Clear current failure mode (only predicting 10 discrete values)

### Why Soft-Decoding Fixes the "Multiples of 5" Problem

The current model predicts LVEF as multiples of 5 (10, 15, 20, ..., 60) because:
1. CE loss treats each digit independently -- predicting "3" instead of "4" in the tens digit is the same loss as predicting "8" instead of "4"
2. The model learns to predict the most common digit values (0 and 5 dominate the training distribution for units digits)
3. There's no signal that predicting 35 when GT is 38 is better than predicting 35 when GT is 55

Soft-decoding fixes this by:
